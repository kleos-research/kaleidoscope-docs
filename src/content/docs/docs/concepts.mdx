---
title: Concepts and boundaries
description: "What a profile, a vault, and an account are in Kaleidoscope, and the boundary that matters: your local memory versus your account metadata."
---

The boundary that matters is your local memory versus your account metadata —
not merely whether you are signed in.

## Local engine

The proprietary native engine owns the memory algorithm, the canonical vault on
your machine, the graph, ranking, and the stdio MCP behavior. Its source is not
part of the public CLI, client, integration, or skill surfaces.

## Manager and profile

The manager is the half of Kaleidoscope that sets things up rather than storing
anything, and most of it is compiled into the `kscope` command you install.
`kscope init` creates a vault, edits host configuration safely, and installs
agent guidance; `kscope profile create`, `import`, `list`, `show` and `remove`
manage profiles; `kscope profile launch` prints the engine launch descriptor a
host is started with; and `kscope call doctor` is the offline diagnostic.

The account and device half is not in that command. Signing in, binding a
profile to an account, and listing or revoking devices belong to a separate
`kaleidoscope` executable, which is published on no channel — so those are
commands you cannot obtain, rather than commands you can run. A profile may hold
one explicit account UUID reference locally; that changes neither its vault
identity nor its credentials.

## What gets installed

You install one package, `@kleos-research/kaleidoscope` from npm, and it brings
in a second package built for your platform. The npm package holds the full
public client, the typed resolver that finds the installed payload, and the
`kscope` command. The platform package holds a single program: the proprietary
engine as object code, with the setup half of the manager compiled into it.
Neither one contains engine source, and neither downloads anything at install
time.

A Python package is intended and not published. `kscope-memory` on PyPI is a
0.0.0 placeholder that says so itself, so there is no Python route in today.

## One profile, every tool

Codex, Claude Code, Cursor, OpenCode, framework clients, and generic MCP clients
are consumers of the same profile. They do not become separate memory stores
merely because their configuration formats differ.

## Account identity

Signing in is designed to link a product account and a device. None of it is
something you can do today: there is no service to sign in to, and the commands
that would do it are in the manager executable that is published on no channel.
The account protocol rejects memory fields and absolute local paths before
transport. Signing out or unlinking is not a vault operation, and must not be
read as consent to upload memory.

## Hosted memory

A hosted service is a later product requiring separate authorization, tenant
isolation, retention, residency, deletion, sync, billing, and incident-response
contracts. It does not exist, and signing in does not opt you into it.
